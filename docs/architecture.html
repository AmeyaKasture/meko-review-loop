Meko Review Loop v0.4.0 · workflow and architecture

Implement, review with fresh eyes, answer the PR, learn

Works with Claude Code, Codex, Cursor, Gemini CLI, or any agent that can follow a Markdown skill and run shell commands. Your main thread writes the code. Unbiased reviewers who never see its reasoning apply your team's review skill and the repository's rule files. The main thread fixes what is valid, explains what is not, and flags doubtful items as design differences. After you push, the same thread answers the PR comments. At the end, the exit step asks the main thread why it missed each valid finding, and revises its author guide so that class of miss does not recur. Only the main thread ever reads that guide.

00At a glance

Reviewers stay unbiased

They get only a generated brief: the diff range, your stated requirements, the rule files, and the team review skill. No author guide, no history, no MCP, no edits.

Three outcomes per finding

Valid: fix it and diagnose why it was missed. Not valid: keep the code and give the reason. Doubtful: keep the code and list it first in the report as a possible design difference.

Same thread answers the PR

After you push, /review-loop:respond ingests the open comments, triages them the same way, re-reviews any fixes, and drafts replies. It posts them only after your explicit yes.

The main thread gets better

/review-loop:exit turns each miss cause into an edit of a topic-organised author guide, per your EXIT.md, shown as a diff for your yes. A hook loads it into future main sessions only.

01Setup

One pasted sentence, in any agent, installs Meko Review Loop and configures the repository. Nothing is committed.

Set up Meko Review Loop for this repository by following
https://github.com/AmeyaKasture/meko-review-loop/blob/main/docs/SETUP.md

  1. Install

    install.sh --agent claude|codex|cursor|gemini|agents: the plugin for Claude Code, or the skills copied into the agent's skills directory. Skipped if already installed.

  2. Survey (read-only)

    Build manifests, CI jobs, contributor docs, rule files (AGENTS.md, CLAUDE.md, REVIEW.md, BUGBOT.md), existing review skills, and the typical size of merged changes.

  3. Draft and ask once

    Two to five fast checks that mirror CI, size limits a little above the usual change, and, if the repository has none, a review skill filled in from a template. You choose: private or committed settings, where the skill goes, which agents and models review, and where the author guide lives.

  4. Meko

    If Meko is not installed or not running, it asks whether to install, start, and connect it to your agent; on yes it does so and points the author guide at it.

  5. Write and prove

    Files are written (with a diff first if one exists), then rl.py config --probe runs each check once. A check that cannot run in this environment is replaced before it can block a loop.

Once installed, the setup skill (/review-loop:setup in Claude Code, review-loop-setup elsewhere) repeats the later steps in any repository.

02The workflow

Eight steps. Steps 2 to 4 repeat until a round is clean, and step 7 reuses them for PR comments.

1 · Main thread

Implement

You and your agent write the code. The author guide is already in context.

2 · Fresh agents

Review round

Snapshot the tree, run checks, then spawn 2 reviewers that apply the review skill and rule files. Later rounds: 1 full + 1 delta.

3 · Main thread

Triage

Valid / not valid / doubtful. Calling a major not valid needs a neutral verifier.

4 · Main thread

Fix + why missed

Fix valid findings and record the cause while fresh: fixed --cause … --why …

5 · New process

Gate

A separate agent process (any CLI, ideally another vendor's model) reviews the identical tree, with no author guide.

6 · You

Report, then push

Design differences come first, then fixes and not-valid reasons. You commit and push.

7 · Same thread

Respond to PR

Ingest open comments, triage, fix, re-review, draft replies, and post on your yes.

8 · Main thread

Exit

Miss causes become a revision of the author guide, which feeds step 1 next time.

The competence loop

valid fix → why did I miss it?→ exit: revise guide per EXIT.md (diff, your yes)→ Meko datapack, or ~/.review-loop/guides/<owner>__<repo>.md→ session start→ main thread only→ fewer bugs next time

When a guide item is clearly a team rule, the exit step proposes it as an AGENTS.md rule (it never edits the file itself). Once you add it, the pattern becomes a team rule that both authors and reviewers apply. The guide is private to the author; rules are shared and versioned.

How it is enforced. The author guide reaches only the author session (in Claude Code through a SessionStart hook, which subagents do not run). Headless reviewers and the gate start as new processes with only the brief; the claude preset also disables hooks and MCP. Reviewer agents have Edit, Write and every mcp__* tool removed. Their prompt is one line, the path to a generated brief, and the brief and agent definitions tell them never to read ~/.review-loop/, the loop's state, or any memory service.

One soft spot: reviewers keep Bash so they can build, test and reproduce bugs. Nothing technically stops them from cat-ing the local guide or calling a store's command line; only their instructions do.

04The review: your team's skill inside the loop

06After you push: answering PR comments

  1. /review-loop:respond 128 in the same thread

    Runs rl.py reopen --pr 128, snapshot --kind pr, and pr-ingest, which reads unresolved threads, review bodies and PR comments through gh. It skips resolved threads, your own comments, and comments it has already seen.

  2. Triage each comment the same three ways

    It reads the whole thread first. Valid comments are fixed, and the miss is diagnosed (why did the loop and the author both miss it?). Not-valid ones get a reason, with a verifier for major ones. Doubtful ones become design differences.

  3. Fixes go back through fresh review

    Any change made for a comment triggers a normal round (full + delta) and the gate. PR-driven fixes are never exempt.

  4. Drafts, then your push, then your yes

    pr-replies writes .review-loop/pr-replies.md and posts nothing. After you push and approve, pr-replies --post replies in each thread with the reply_prefix (default [AI] ). It refuses while fixes are uncommitted or unpushed, and it never resolves threads or approves.

07Exit: why did I miss it, and what must the guide say?

The exit step does not dump lessons into a file. It diagnoses each miss, then edits one coherent instructions document.

Step 1: the main thread diagnoses every valid finding

It records one cause, ideally while fixing (when it still remembers writing the code), otherwise at exit. Before choosing, it searches the guide and the rule-file chain for guidance that already covered the issue. "Covered" causes must quote that guidance.

CauseMeaningWhat changes in the guide
not-coveredNo guidance existedAdd guidance in the topic section where an author would look, saying when it applies and why.
covered-unclearGuidance existed but was vague or buriedRewrite that item so the trigger and action are unambiguous. No second item.
covered-ignoredClear, but not appliedNo new text. Move it to "Before you finish", tie it to the moment it matters, or make it a concrete check.
context-gapNeeded code or system knowledgeAdd a "Where to look" pointer.
spec-gapThe requirement was unclearOptionally a question under "Before you start".
one-offA slipNothing.
A design difference you decidedRecorded under "Design decisions", with the reason.

Step 2: revise the author guide as a document

One guide per repository, structured by your EXIT.md. Several findings with one root cause become one edit, overlaps are merged, superseded text is deleted, and the guide stays within its size budget (about 7,000 characters). Finding ids, dates and counts never go in the body; they go to …history.md.

## Before you start
- Does this change alter a stored or public format? Ask if the spec is silent.
## While writing
### Error handling
- When a helper can fail, return the error with context (operation, object);
  never exit the process inside it (root AGENTS.md, "Error handling").
### Persistence and compatibility
- Renaming a serialised field breaks data written by older versions;
  add a migration or keep the old name.
## Where to look
- Before changing request batching, read the callers in src/batch/:
  retries reuse the batch object.
## Design decisions
- Lookups go through the cache layer: called per row (PR review, confirmed).
## Before you finish
- [ ] Every read of an optional field handles the missing case.
- [ ] No warn-and-continue on an unexpected state.

Step 3: you approve the diff

The exit step prints the miss table and diff -u of the guide, and asks you to apply it, edit it first, or skip it. Only on "apply" does it save a new guide version and one history entry for the loop (never twice for the same loop). Team-wide items are proposed as exact AGENTS.md text; it never edits that file.

Your instructions file, ~/.review-loop/EXIT.md, defines the sections (Before you start, While writing by topic, Where to look, Design decisions, Before you finish), the writing style, the budget, the approval rule, and the destinations. Edit it, and every later exit follows it.

Meko

Meko, a local, offline memory engine, keeps each repository's guide in a datapack (review-loop guide <owner>/<repo>): every approved revision is a version of author-guide.md, and each loop's miss history is a searchable memory. Any agent connected to Meko (Claude Code, Codex, Cursor, OpenCode, Kiro) can recall it; reviewers are never connected. The setup skill installs and connects it on request, and scripts/stores/meko_store.py plugs it in through the store commands below.

Any other store

To keep every version elsewhere (a private git repository, a synced folder, another memory service), set two commands in ~/.review-loop/settings.json. The local file becomes a cache and the fallback when the store is unreachable.

{
  "guide_store": "auto",
  "guide_pull_cmd": "git-store.sh pull",
  "guide_push_cmd": "git-store.sh push"
}
CommandGetsMust
guide_pull_cmdRL_REPO_SLUGPrint the newest guide (nothing if none); exit non-zero if the store is unavailable.
guide_push_cmdRL_REPO_SLUG, RL_GUIDE_FILE, RL_HISTORY_FILE, RL_MARKERStore the new version and history; optionally print a version id.

guide_store is auto (use the commands, fall back to the local copy), command (a failed save is an error), or file. examples/guide-store/git-store.sh is a complete store backed by git.

What the main thread reads before it writes code

session start
  ├─ AGENTS.md / CLAUDE.md / …      (repo rules, loaded by the agent)
  └─ rl.py learnings-context        (Claude Code: SessionStart hook; others: --text, or the agent's own hook)
        └─ newest author guide  (Meko or another store, else local file)
main thread writes code

09How to use it

# 0. once per repository
/review-loop:setup
# 1. implement in a normal session
# 2. harden it
/review-loop:review-loop                 # branch + uncommitted vs main
# 3. read the report; answer design differences; then push yourself
# 4. once the PR has comments, in the same session
/review-loop:respond 128
# 5. when the PR is done
/review-loop:exit
