# review-loop: fresh-context review, fix, repeat

A Claude Code skill that turns "a second AI with a fresh context always finds
bugs" into a repeatable, bounded process.

```
/review-loop:review-loop                      # current branch + uncommitted changes vs default branch
/review-loop:review-loop 1234                 # check out PR #1234 and harden it
/review-loop:review-loop main --strict        # loop until no minor findings either
/review-loop:review-loop --gate-model sonnet  # final gate on a different model
```

## Why this works

The session that wrote the code shares the assumptions that produced its bugs.
Asking it to "double-check" re-reads the code through the same mental model.
A reviewer with an empty context sees the diff the way a stranger does.
Published experience agrees: context isolation, not raw capability, is what
recovers most of review's value, and a different model adds further diversity.

But a naive loop ("review, fix everything, repeat") fails in four known ways:

| Failure mode | What goes wrong | Countermeasure here |
|---|---|---|
| **Author bias in triage** | The author session dismisses real bugs as "intentional". | Rejecting any major or high-confidence finding requires a neutral `finding-verifier` agent. The script refuses the rejection otherwise. |
| **Anchoring the reviewer** | The orchestrator summarises the change or lists what it fixed, and the reviewer inherits its blind spots. | Reviewers receive one line: the path to a brief generated by the script from git refs and the stated requirements. No author prose reaches them. |
| **Never converging** | LLM reviewers can always find a nit, so "loop until zero" never ends. | A severity threshold (major by default) decides convergence. A round cap ends the loop. Nits never trigger another round. |
| **Oscillation** | Round 2 undoes round 1's fix, round 3 redoes it. | A ledger fingerprints findings across rounds. A recurrence of a fixed issue is a regression; a second recurrence becomes a question for you. |

Three more problems are handled mechanically:

- **Unreviewed final edits.** The code that ships must be exactly the code the
  last clean review saw. After a clean round, code edits are forbidden.
  Accepted minor findings become optional fixes in the report.
- **Context leaking through connectors.** Reviewer agents have every MCP tool
  removed, and the gate process loads no MCP servers and no hooks. Otherwise a
  memory connector could hand a reviewer the author's own
  captured conversation.
- **Premature stopping.** A Stop hook nudges the orchestrator back into the
  loop while it is running. It never traps you: it only fires for the owning
  session, at most three times per round.

## Architecture

```
 main session (author context, orchestrator, fixer)
 │
 ├─ rl.py init / snapshot / run-checks / brief        deterministic state engine
 │
 ├─ round N ──► fresh-reviewer A ─┐  parallel, read-only, no author context
 │             fresh-reviewer B ─┤  run checks, reproduce bugs, write JSON
 │                               ▼
 ├─ rl.py ingest  ──► ledger (.review-loop/state.json)
 │
 ├─ triage: accept | reject | defer | ask | duplicate
 │            │ reject major? ──► finding-verifier (neutral) ──► REAL / NOT_REAL / UNCERTAIN
 │
 ├─ fix accepted ──► rl.py fixed ──► rl.py status ──► NEXT_ROUND | GATE | CONVERGED | CAPPED
 │
 ├─ gate ──► headless-review.sh ──► separate process of any agent CLI
 │                                   (claude, codex, gemini, cursor, custom),
 │                                   optional different vendor or model
 │
 └─ report (.review-loop/report-*.md) ──► the user is asked about every judgement call
```

Round 1 uses two full reviewers with different lenses. Later rounds use a
dual path: one fresh full review, plus one review of only the fix delta, which
is where regressions hide.

## Components

| File | Role |
|---|---|
| `skills/review-loop/SKILL.md` | The orchestration protocol Claude follows in your main session. |
| `skills/review-loop/scripts/rl.py` | State engine: snapshots, checks, ledger, triage rules, convergence decision, Stop guard, report. |
| `skills/review-loop/scripts/fresh-session-review.sh` | Gate review in a brand-new headless Claude process with `--json-schema`, no MCP servers, and no hooks. |
| `skills/review-loop/reference/reviewer-brief.md` | The fixed brief template every reviewer receives. |
| `skills/review-loop/reference/findings.schema.json` | Output contract for reviewers. |
| `skills/review-loop/reference/triage-rubric.md` | Rules the author session must follow when judging findings. |
| `agents/fresh-reviewer.md` | Read-only reviewer agent: Edit, Write, and all MCP tools removed. |
| `agents/finding-verifier.md` | Neutral adjudicator for disputed findings, with the same restrictions. |
| `hooks/hooks.json` | The Stop guard, gated on loop state and session id. |

Paths are relative to `plugins/review-loop/`.

### Snapshots without touching your branch

Each round's tree, including untracked files, is captured as a commit under
`refs/review-loop/round-N` using a temporary git index. Your HEAD, index, and
stash are never touched, and nothing is committed to your branch. Reviewers
diff `base..round-N`. Delta reviewers diff `round-(N-1)..round-N`. After each
review, `verify-tree` confirms the reviewer did not modify files (build
artifacts excepted).

### Severity and convergence

| Severity | Meaning | Blocks convergence? |
|---|---|---|
| blocker | Wrong results, crash, data loss, security hole, failing check | Yes |
| major | Realistic bug, contract break, check warning in changed code, missing requirement | Yes |
| minor | Real but low impact | Only with `--strict` |
| nit | Taste | Never |

Converged means: a review round accepted nothing blocking, checks passed, and
then a gate review in a completely new session also accepted nothing blocking
on the identical tree.

## Configuration

| Flag | Default | Effect |
|---|---|---|
| `--max-rounds N` | 5 | Hard cap on review rounds. One gate may run after the cap. |
| `--strict` | off | Minor findings also block convergence. |
| `--no-gate` | gate on | Skip the separate-process gate review. |
| `--gate-model M` | session default | Model for the gate, such as `fable` or `sonnet`. Prefer one different from the author. |
| `--checks "a;;b"` | auto-detected | Exact check commands. Essential for large repos where full suites are slow. |
| `--reviewer-model M` | inherit | Model for reviewer agents. |

All of these can also live in `.review-loop.json` at the repository root.

## Cost and time

Each round costs roughly two reviewer agents, plus verifier agents for
disputed findings. On the test repository, a Sonnet gate review cost about
fifteen cents. A typical feature PR converges in two or three rounds. The
biggest lever on cost and wall-clock time is the check set: targeted tests
beat whole-repo suites.

| Project | Idea worth borrowing | Gap this design fills |
|---|---|---|
| [winrey/claude-code-toolkit](https://github.com/winrey/claude-code-toolkit) | Fresh reviewers each round, finding verification, dual-path re-review | Adds a durable ledger, oscillation handling, and a separate-process gate |
| [mintmcp/dev-loop](https://github.com/mintmcp/dev-loop) | Cross-model review (Codex plus Claude), persisted state, stop hooks | Works without Codex; enforces verifier-backed rejections |
| [tomek7667/reviewloop](https://github.com/tomek7667/reviewloop) | Pins requirements as an acceptance list; escalates oscillating findings | Does not blindly fix every finding; triages with a rubric |
| [vdor/agent-review-loop](https://github.com/vdor/agent-review-loop) | Multiple reviewer angles, round cap | Adds deterministic checks and reproduction as evidence |
| Official `code-review` plugin | High-signal filtering and per-finding validation agents | Single pass; no fix loop. Reviewers here may invoke it as an extra lens |
| Official `ralph-loop` plugin | Stop-hook loop inside one session | Same context throughout, so no independence; this design uses the hook only as a guard |

## Extending it

- **Cross-vendor review.** Set `gate_agent` (or `reviewer_agent`) to a
  different vendor's CLI from the author's agent, or run a second gate with
  `headless-review.sh --mode gate --name gate2 --agent <other>`. Different
  model families miss different bugs.
- **More lenses.** Name extra review agents or skills your agent offers
  (for example silent-failure or type-design reviewers) in reviewer lenses.
- **CI.** The headless runner works unchanged in a CI job, since it only
  needs an agent CLI, Python, and git.
- **Workflow tools.** For fully deterministic orchestration across many PRs,
  the same protocol can be driven by an agent's workflow or scripting
  feature, since every step is an `rl.py` command.
